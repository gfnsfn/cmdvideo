# cmdvideo —— 在 cmd 窗口里放视频 / 投屏别的窗口

一个 Windows 小工具，两件事：

1. **放视频** —— 把视频渲染成彩色字符，直接「投影」进 cmd / Windows 终端窗口播放。
2. **投屏窗口** —— 把系统里**任意一个正在运行的程序窗口**搬进 cmd 里用彩色字符画
   显示，而且能用鼠标和键盘**操控那个程序**。

**下载**：到 [Releases](https://github.com/gfnsfn/cmdvideo/releases/latest) 拿现成的

| 文件 | 说明 |
|---|---|
| **cmdvideo_setup.exe** | **推荐**。一键安装，`ffmpeg.exe` 一起装好，装到当前用户目录、不需要管理员 |
| cmdvideo.exe | 免安装单文件。**要放视频就得把 `ffmpeg.exe` 放在它旁边**（投屏不需要） |
| ffmpeg.exe | 上面那个单文件版缺的就是它（87 MB，官方 Windows 构建） |
| SHA256SUMS.txt | 校验值 |

单文件版没有 `ffmpeg.exe` 时，点「开始播放」会直接弹窗告诉你缺什么 —— 不会静默失败。

## 1.8 修了什么

- **投屏时滚轮没法用。** 一共四个原因叠在一起，全修了：

  1. **屏幕坐标算错了一个分量（最隐蔽的一个）。** `ClientToScreen` 要的是
     `POINT`（两个 4 字节 LONG），代码里传的却是控制台 API 用的 `COORD`
     （两个 2 字节 SHORT，只有 4 字节）—— Windows 按 LONG 写回，越过结构体
     末尾，于是**只有 x 对、y 永远是 0**：

        实测 `ClientToScreen(0,0)` 用 `COORD` 得到 `(214, 0)`，用 `POINT` 才是 `(214, 208)`

     y 错了，滚轮就被投到「屏幕上另一个位置的窗口」去了，而 `PostMessage`
     照样返回成功 —— 日志一切正常、画面纹丝不动。
  2. **滚动消息要投给鼠标底下那个子窗口，不能投给顶层窗口。**
     `WM_MOUSEWHEEL` 和 `WM_LBUTTONDOWN` 不一样，**不会沿着窗口层级往下转发**；
     记事本这类程序真正处理滚动的是里面一层控件（`RichEditD2DPT`），顶层窗口
     收到就晾着。现在沿目标窗口自己的层级往下钻
     （用 `ChildWindowFromPointEx`，**不能**用 `WindowFromPoint` —— 投屏窗口
     盖在上面，那个 API 只会返回投屏窗口自己）。
  3. **小于一格的滚动被整数除丢掉了。** 原来直接 `delta // 120` 换算格数，
     而平滑滚动 / 高精度滚轮发的是 ±30、±60 这种不足一格的增量，除以 120 全是 0
     —— 一条都发不出去。现在攒余数，攒够一格才转发。
  4. **移动事件把目标窗口的消息队列灌满了。** 鼠标快移时一拍内几百个移动事件
     原来全量投递，队列堆到两千条；Windows 消息队列超上限后会**静默丢消息**
     （`PostMessage` 仍返回成功），滚轮首当其冲。现在同一拍合并成一条，
     实测一次快速拖动从投 2000 条降到 2 条。

  另外加了两道保险：控制台不是前台窗口时滚动会先把投屏窗口抢回前台（滚轮只有
  前台窗口才上报）；万一还有控件不认投递过来的滚动消息，就看滚动位置判定，
  没动就补一条经典 `WM_VSCROLL`（**不碰系统光标**）。

  实测结果：投屏记事本（400 行）上下滚动，画面指纹前后不同、双向都能滚。

## 1.7 修了什么

- **「点了开始播放没反应」。** 原因是 `ffmpeg.exe` 不在 `cmdvideo.exe` 旁边。
  播放是在**另一个控制台**里跑的，那个进程找不到 ffmpeg 会立刻以退出码 2
  结束 —— 窗口一闪就没了，界面上什么提示都没有，看起来就是「点了没反应」。

  两处都堵上了：

  - **先检查再启动。** 图形界面点「开始播放」之前自己先找一遍 ffmpeg，
    找不到就弹窗说清楚「把 ffmpeg.exe 放到 cmdvideo.exe 同目录」，
    底部状态栏也写一行，不再对着空气猜。
  - **多兜几个位置。** 除了「程序旁边」和 PATH，现在还会看当前工作目录、
    源码目录（脚本模式）、以及程序旁边的 `bin\ffmpeg.exe`。安装包的标准布局
    本来就是 `cmdvideo.exe` + `ffmpeg.exe` 放同一层，单独把 exe 拷出来就会缺它。

  已确认：修好后播放窗口正常出画面（201×52 字符网格、9,231 个非空格子、
  119 种颜色属性 —— 真在放视频，不是空白窗口）。
- **点一下投屏画面，光标和窗口就跳走。** 1.6 改成「按下时把系统光标搬到目标
  窗口上、并把目标窗口提到前台」之后，点一下就有两个副作用：鼠标指针跑到目标
  窗口那边去了、投屏窗口退到后面。用户视角就是「点完就跳转到原来的窗口」，
  还得再点一次投屏窗口才能接着用。

  现在默认形态**一个系统 API 都不碰**：鼠标和键盘全部当消息投给目标窗口，
  光标留在原地、前台不切换、投屏窗口始终在最前面。点击照样落到目标程序上
  （目标窗口会收到 `WM_LBUTTONDOWN/UP`，拖拽时 `WM_MOUSEMOVE` 也带着按键状态）。

  想要老行为（真搬光标、真切前台）的，命令行加 `--real-takeover`。**这个开关
  故意不放进图形界面** —— 它会真的把光标搬到目标窗口上，表现就是「点一下光标
  闪到目标窗口那边去」，摆在那儿只会被误点。
- 顺带把「真实按键要目标窗口在前台」这件事收敛了：只有 `--real-takeover`
  才会去切前台，默认形态一次都不切。

## 1.6 修了什么

- **「真实操控」一开，鼠标就进不了窗口了。** 这是个大 bug，根因是个正反馈环：

  ```
  鼠标动一下 → 控制台上报一个新格 → 程序把系统光标搬到目标窗口对应位置
            → 光标在新位置又被控制台上报成一个新格 → 再搬 …… 无限循环
  ```

  结果是光标满屏乱飞（实测一次注入移动后，光标在 1 秒内自己跑了几百像素），
  而且**再也出不掉**投屏窗口 —— 每出现一个新格都把它拽回去，想点到别的窗口
  根本做不到。

  现在改成：**纯悬停绝不动系统光标**，只有「按下 / 拖拽 / 滚轮」这三件事才
  把它送到目标窗口上。悬停效果照旧（走 `PostMessage`），点下去那一下依旧是
  货真价实的系统点击。实测：4 次悬停移动，修之前调了 4 次 `SetCursorPos`，
  修之后 0 次；真的点击仍然完整落到目标窗口（目标窗口自己数到了那一下）。
- 顺带把「按下去之后把目标窗口弄到前台」改稳了：`SetForegroundWindow` 会被
  前台锁定挡掉，现在按 `AttachThreadInput` 借权限 → 模拟一次 Alt → 兜底置顶
  的顺序试，而且不在渲染线程里做（不然会掉帧）。
- `--real` 目标窗口已最小化时不再把它从任务栏拽出来；输入线程就绪前多等 0.12 秒，
  免得刚开画面那一下的鼠标事件丢掉。

## 1.5 修了什么

- **去掉了鼠标悬停时弹出来的那个黄色小提示框。** 1.4 里为了看被截断的完整路径加过它，
  实际用起来很烦（鼠标扫过去就弹），已经整个删掉。
- 视频路径和窗口标题改成**限宽自动换行**：宽度被钉死在 440 像素以内，放不下就换行，
  **完整路径照样看得到**，不再需要任何提示框，界面宽度也不会被长路径撑开。

## 1.4 修了什么

- **选了长路径之后「开始播放」不见了。** 原因：视频路径、窗口标题这类长文本会让
  `ttk.Label` 按整段文字申请宽度，把整块界面撑宽；而窗口尺寸是**启动时**（还没选文件、
  文本很短）就定死的，于是内容比窗口宽，右边一截被裁掉 —— 正好是「浏览…」和「开始播放」。
  现在这类长文本一律**限宽**，界面宽度不会再随着你选了什么文件而变。
- **内容区改成真正可滚动了。** 之前的注释里写着「可滚动」，其实只是个普通 Frame，
  并没有实现。现在内容真的放在 Canvas 里：内容再高也只会出竖向滚动条，
  **绝不会把底下的按钮顶出窗口**；窗口被压窄时先出横向滚动条，
  按钮栏始终保留自己的位置（按钮永远点得到）。
- 窗口现在**可以放大**了（字大/屏幕大时可以拉宽），
  并且会按屏幕尺寸自动收敛，不会再出现「窗口比屏幕还大」的情况。

## 怎么用

### 方式一：开始菜单 / 桌面（推荐）

打开 `cmdvideo`，窗口里：

1. **视频文件** → 点 `浏览...` 选一个视频
2. **播放画法** → 选色块还是字符
3. 点 **开始播放**

播放会**另开一个 cmd 窗口**，并且**自动把这个窗口放大到接近满屏**，
画面铺满整个窗口。

> **主窗口不会关。** 播放窗口关掉之后，主窗口还在那儿，可以再点一次「开始播放」
> 播别的视频，或者换个画法再播一遍。想退出就点「取消」或右上角的叉。

### 方式二：把视频拖到 exe 上

拖进去同样会弹出选择框，文件已经填好，选个画法按开始播放。

### 方式三：命令行（可脚本化）
```
cmdvideo 视频.mp4 --mode chars
cmdvideo 视频.mp4 --cols 100 --fps 20 --loop
```

## 投屏另一个窗口（还能操控它）

界面里「**投屏另一个窗口**」那一段：

1. 点 **选择窗口...**，弹出的列表里挑一个正在运行的程序（有标题、进程名、尺寸）
2. 想真操控就勾上 **真实操控**（见下面「两种操控方式」）
3. 点 **开始投屏**

会另开一个 cmd 窗口，把那个程序的画面用彩色字符画显示出来，
窗口最底下有一行提示条写着操作方式。

投屏窗口里按 **`Ctrl+Q`** 退出（特意没用 Esc，因为 Esc 要留给目标程序用）。

### 能操控什么

| 操作 | 效果 |
|---|---|
| 鼠标移动 | 转发给目标窗口（目标窗口会显示自己的悬停效果） |
| 左键 / 右键 / 中键 按下抬起 | 转发，含拖动（按住移动） |
| 滚轮 | 转发 |
| 键盘 | 转发（同时发 `WM_KEYDOWN` 和 `WM_CHAR`，这样既认快捷键也认文本输入） |

### 两种操控方式

| 方式 | 原理 | 适合 |
|---|---|---|
| **默认（推荐）** | `PostMessage` 往目标窗口的消息队列里塞消息 | 不抢走你真实的鼠标键盘 —— 投屏里的操作和你在别的窗口干活互不干扰 |
| **真实操控** | `SendInput` / `SetCursorPos`，真的移动系统鼠标、真的按键 | 碰到不认 `PostMessage` 的程序（部分浏览器、游戏）时用；但**会真的占用你的鼠标键盘**，而且需要目标窗口在前台 |

#### 真实操控什么时候动你的鼠标（1.7 起：默认一个系统 API 都不碰）

**默认形态**：开了真实操控，鼠标、键盘**全部当消息投给目标窗口**。
你的系统光标留在手底下不动，前台窗口也不换，投屏窗口一直待在最前面 ——
所以画面上你点哪儿就是点哪儿，点完那一下不会「跳走」。

> 1.6 及以前，按下去的那一刻会把系统光标搬到目标窗口对应位置、并把目标窗口
> 提到前台。结果就是点一下画面，光标和窗口双双跳走，得再点一次投屏窗口才回来。
> 1.7 把这个副作用整个去掉了 —— 点击照样送到目标程序，但不再搬光标、不再切前台。

**接管形态**（启动投屏时勾「接管鼠标」/ 命令行 `--real-takeover`）才真的动系统：
按下 / 拖拽 / 滚轮会把系统光标搬到目标窗口上，并按下去补一次真实点击，键盘走
`keybd_event`。留给那些不认消息、非要真实输入的程序（部分游戏）。
代价也写清楚：光标会被搬走、目标窗口会被提到前台、投屏窗口退到后面。

**为什么连「跟着鼠标搬光标」都不能做**（1.5 的老 bug）：

> 光标一动就被搬走，控制台在新位置又上报一个格子，于是再搬一次……
> 同一个窗口里形成正反馈，几个像素的抖动会被放大成满屏乱飞，而且光标
> 再也出不了投屏窗口。现象就是「鼠标根本进不了窗口」。

| 形态 | 光标 | 前台窗口 | 点击怎么到目标 | 适合 |
|---|---|---|---|---|
| 默认（推荐） | 不动 | 不换 | 消息（`WM_*BUTTON*`） | 浏览器、聊天工具、绝大多数程序 |
| 接管（`--real-takeover`） | 会被搬到目标窗口上 | 会切到目标窗口 | 真实 `SendInput` 点击 | 不认消息、非要真实输入的游戏 |

### 画面是怎么抓的

默认是 **自动**，两种抓法会自动挑：

| 抓法 | 原理 | 特点 |
|---|---|---|
| `PrintWindow` | 让目标窗口把自己画到内存位图上 | **窗口被别的窗口挡住、不在最前面也能抓到完整画面**；但少数程序（硬件加速、UWP、任务管理器这类）会返回全黑 |
| 抓屏 `BitBlt` | 从屏幕 DC 直接抠那一块 | 一定能抓到，但**要求窗口露在最前面**，被挡住就抓到挡它的东西 |

「自动」模式会先试 `PrintWindow`，如果结果是全黑（抽样判断）就自动退回抓屏。
也可以手动指定：命令行 `--capture print` / `--capture screen`。

抓到的原图再用 `StretchBlt` 一步缩放到字符网格的尺寸，全程走 GDI，
Python 这边只碰一次内存块。

### 命令行投屏

```
cmdvideo --list-windows              # 列出所有可以投屏的窗口（含句柄）
cmdvideo --window "记事本"            # 按标题关键字投屏
cmdvideo --window 133602             # 按窗口句柄投屏
cmdvideo --window "Steam" --mode chars --fps 15
cmdvideo --window "Steam" --capture screen    # 强制用抓屏方式
cmdvideo --window "Steam" --real              # 真实操控（不碰你的光标/前台）
cmdvideo --window "Steam" --real-takeover     # 接管鼠标：真搬光标、真切前台
```

### 坐标怎么对上

控制台上报的鼠标事件直接带着「第几行第几列字符」，所以映射很直接：

```
目标客户区坐标 = 字符格坐标 ÷ 字符网格大小 × 目标客户区像素大小
```

因为字符网格本来就是按目标窗口的宽高比算出来的，这个线性映射是准的。
实测：目标客户区 1435×852、字符网格 172×51 时，点第 (10, 5) 格 →
换算成客户区 (83, 83)，发出去的 `WM_LBUTTONDOWN` 的 lParam 正是 (83, 83)。

### 投屏的已知限制

- 抓帧速度取决于目标程序响应 `PrintWindow` 的速度，一般 **10~30 fps**，
  默认限 20fps。**如果目标程序卡住了，`PrintWindow` 会跟着一起卡** —— 这时
  改用 `--capture screen`。
- 字符分辨率下鼠标精度有限：一格大约对应「目标窗口宽度 ÷ 字符列数」个像素
  （上面那个例子里一格约 8 像素）。点小按钮要靠运气，换哪种操控形态都没用，
  精度瓶颈在字符网格本身。
- 真实操控的默认形态走消息投递，所以**完全不理消息、只认真实输入的程序**
  （少数游戏/反作弊严格的应用）可能收不到，这时候改用 `--real-takeover`。
- 全屏独占的游戏（DirectX 独占全屏）通常抓不到画面，改成窗口化/无边框再试。
- 投屏不支持音频（本来也没法放）。

## 三种画法

### `--mode block` —— 色块（默认，最细腻）

每个字符格用 `▀`（上半块）表示：前景色涂格子上半部、背景色涂下半部，
于是一个字符格承载 **2 个纵向像素**，画面细腻度翻倍。看起来最接近原片。

### `--mode chars` —— 彩色字符

每个字符格是一个真正的字符：**字符的疏密表现明暗，前景色表现色彩**。
经典的黑客风字符画，但带颜色。输出量只有色块模式的三分之一左右。

明暗阶梯（界面里的 **字符阶梯**，或命令行 `--ramp`）有五个预设：

| 名字 | 阶梯 | 效果 |
|---|---|---|
| `ascii` | ` .:-=+*#%@` | 10 级，通用（默认） |
| `dense` | 70 级长阶梯 | 细节最多，但很吃字体 |
| `blocks` | ` ░▒▓█` | 方块阴影，颗粒感最强、最「实」 |
| `simple` | ` .:-=+*#` | 8 级，干净 |
| `dots` | ` ·•●` | 点阵风 |

也可以直接给一串自定义字符，比如 `--ramp " .oO@"`。
界面里选「自定义」后右边的输入框会变成可编辑，旁边会实时预览效果。

### `--mode gray` —— 黑白

画法和色块一样，只是去掉颜色。最快。

## 分辨率自动适配

**不用手动设分辨率。** 程序会：

- **先把播放窗口自动放大到接近满屏**（占屏幕约 95% × 90%），并把字体调到 18px
- 读取视频的原始宽高比
- 读取当前窗口的字符行列数，并**量出字符格的真实像素高宽比**
- 按比例缩放，算出填满窗口又不变形的字符网格

实测：1920×1080 的屏幕上，播放窗口会从默认的 `80×25` 字符
放大到 **`201×52` 字符（约 1825×975 像素）**，
有效画面从 1,920 个字符格涨到 9,231 个 —— **面积约 4.8 倍**。

### 关于「比例」这件事（踩过的坑）

算网格的时候有**两个完全不同的概念**，早期版本把它们混在一起，导致
**彩色字符模式被横向压扁了一半**：

| 概念 | 含义 | 取值 |
|---|---|---|
| **字符格的物理高宽比** | 一格在屏幕上有多高多宽。等宽字体通常 ≈ 2.0（高是宽的两倍） | 由**字体**决定 |
| **每格的纵向采样像素数** | 渲染时一格吃几个视频像素。`▀` 半块画法吃 2 个，一个字符一格吃 1 个 | 由**画法**决定 |

决定「看起来像不像原片」的是**前者**；后者只影响清晰度。
所以正确公式是：

```
显示宽高比 = cols / (rows × 字符格高宽比)   ==   视频宽高比
```

而不是拿「采样像素数」去当「屏幕上的比例」。修正前后对比（480×270 的 16:9 视频）：

| 画法 | 修正前 | 修正后 |
|---|---|---|
| `block` / `gray` | 181 列 ✓ | 181 列 ✓ |
| `chars` | 91 列（**压扁 49.8%**） ✗ | 181 列（偏差 0.2%） ✓ |

程序运行时会调 `guess_cell_aspect()` 实测字符格比例（量不到就退回 2.0），
所以换字体、换字号也不会比例失真。

命令行想手动指定也可以用 `--cols 100`，程序会按比例自动算出对应的高度。

## 关于 ffmpeg

解码交给 ffmpeg。程序按这个顺序找它：

1. 环境变量 `CMDVIDEO_FFMPEG` 指向的路径
2. 本程序同目录的 `ffmpeg.exe` ← **推荐，交付目录已放好**
3. 系统 `PATH` 里的 ffmpeg
4. Python 环境里 `imageio-ffmpeg` 自带的

所以只要 `ffmpeg.exe` 和 `cmdvideo.exe` 放在一起，拷到哪台机器都能直接用。

## 声音

默认会抽出音轨异步播放（winsound 只支持 WAV，所以先转一道）。
循环模式（`--loop`）下不播声音。不想要声音在界面里取消勾选 **播放声音**，
或命令行加 `--mute`。

## 命令行参数

```
cmdvideo 视频.mp4                    # 默认色块彩色，铺满窗口
cmdvideo 视频.mp4 --mode chars       # 彩色字符画
cmdvideo 视频.mp4 --mode chars --ramp blocks
cmdvideo 视频.mp4 --cols 100         # 指定宽度（高度按比例自动算）
cmdvideo 视频.mp4 --fps 20           # 限帧，弱机更流畅
cmdvideo 视频.mp4 --loop             # 循环播放
cmdvideo 视频.mp4 --mode gray        # 黑白，最快
cmdvideo 视频.mp4 --color 256        # 兼容不支持真彩色的终端
cmdvideo 视频.mp4 --mute             # 不放声音
cmdvideo 视频.mp4 --stats            # 结束打印帧率/丢帧统计
cmdvideo --check 视频.mp4            # 检查 ffmpeg 和视频信息
cmdvideo --gui                       # 强制打开选择框
```

投屏相关：

```
cmdvideo --list-windows              # 列出可投屏的窗口
cmdvideo --window "关键字"            # 投屏指定窗口（标题/进程名/句柄）
cmdvideo --window "关键字" --real     # 用 SendInput 真实操控
cmdvideo --window "关键字" --capture screen
cmdvideo --window "关键字" --project-fps 15
```

播放中按 `Ctrl+C` 停止；投屏中按 `Ctrl+Q` 退出。

## 播放流畅度（这一版修的重点）

之前的版本**放视频很卡**，尤其是在大窗口 / 高清源 / 60fps 视频下。
把每一帧的耗时拆开量了一遍，瓶颈不在解码（ffmpeg 解码+缩放能跑 1000fps 以上），
而在**渲染**和**往控制台写**这两步：

| 环节 | 优化前 | 优化后 | 说明 |
|---|---|---|---|
| 渲染（185×52） | 8.5 ms | **~4 ms** | Python 逐格拼字符串 |
| 每帧输出量 | 314 KB | **66 KB** | 控制台要解析的转义序列 |
| 写控制台 | 6.6 ms | **~1.5 ms** | conhost 解析转义 ≈ 83 MB/s |
| **单帧合计** | **~13.9 ms** | **~5 ms** | 上限从 ~72 fps 提到 ~200 fps |

做了四件事：

1. **只在颜色真的变了的时候才发转义序列。** 老实现每个字符格都重发
   「前景色 + 背景色」两串转义，一帧要吐 300KB+。真实视频里相邻格大量同色，
   改成分别跟踪前景/背景、变了才发，输出直接砍到 1/5。
2. **行级 diff。** 整行像素和上一帧逐字节一样就整行跳过（配合绝对光标定位
   `\x1b[{行};1H`）。静态内容（暂停画面、字幕、投屏的界面）几乎零开销。
3. **转义串查表 + 颜色打包成整数。** 颜色按 5bit/通道 打包成 15bit 整数当键，
   用 list 懒填充查表，逐格只做一次索引。老实现用 6 元组做 dict 缓存，
   播久了会攒到 **14 万条**，越播越慢（还占内存）。
4. **丢掉追不上的帧。** 每帧按「本来该在什么时候显示」对表，落后超过一帧半就
   直接丢掉不画 —— 宁可掉帧也不能让画面比声音慢，那才是肉眼感觉到的「卡」。
   （另外起跑时间改成**第一帧真正到手时**才对齐：ffmpeg 启动要两三百毫秒，
   算进去的话一上来就白丢好几帧。）

渲染内循环还试过几种写法，最后选了「按行切片 + zip 迭代通道」：
每格省掉两次乘法和两次下标加法，比逐格算下标快约 1.2 ms/帧。
（也试过「6 元组 dict 缓存 + 用 `is` 比较对象同一性来跟踪变化」，渲染更快但
输出多 60%，算上写入的总账反而更慢，所以没采用。）

## 实测数据

480×270 / 24fps / 12 秒的测试视频，185×52 字符网格（1920×1080 屏幕满屏）：

| 模式 | 帧数 | 实测帧率 | 单帧渲染 | 单帧写入 | 每帧输出 |
|---|---|---|---|---|---|
| `block` | 288 | 24.0 fps | 4.2 ms | 1.3 ms | 66 KB |
| `chars` | 288 | 24.0 fps | 3.4 ms | 0.6 ms | 40 KB |
| `gray` | 288 | 24.0 fps | 4.0 ms | ~0.5 ms | 62 KB |

三种模式都跑满 24fps 且**不丢帧**（`--stats` 会打印「读入 N，为跟声音丢掉 M」）。

渲染正确性是**逐格比对**验证的：把输出的转义序列反解析回每个格子的颜色，
再和源像素逐格对比，三种模式各测多帧，**不符格子数为 0**。

投屏实测（目标：Steam 窗口，客户区 1435×852 → 字符网格 172×51）：
鼠标点击、键盘按键、滚轮转发的消息内容与坐标全部核对通过。

## 自己重新打安装包

源码目录里带好了脚本，改完代码想重新出安装包就跑：

```
:: 1. 重新打包 exe（必须用 3.12 的 venv，3.13 没有 tkinter）
.venv312\Scripts\python.exe -m PyInstaller --noconfirm --clean --onefile ^
    --windowed --name cmdvideo --distpath dist --workpath .build312\build ^
    --specpath .build312 cmdvideo.py

:: 2. 重新生成安装包（ISCC.exe 是 Inno Setup 6 自带的编译器，
::    一般在 %LOCALAPPDATA%\Programs\Inno Setup 6\ 或 C:\Program Files (x86)\Inno Setup 6\）
"%LOCALAPPDATA%\Programs\Inno Setup 6\ISCC.exe" cmdvideo_setup.iss
```

产物在 `installer_out\cmdvideo_setup.exe`。

安装包配置都在 `cmdvideo_setup.iss` 里（Inno Setup 6 脚本），
包括安装路径、快捷方式、卸载项、文件关联。注意安装包会把 `ffmpeg.exe`
一起装到 `{app}` —— 播放功能依赖它，单把 `cmdvideo.exe` 拷走是不能放视频的
（程序会明确提示缺 ffmpeg，而不是静默失败）。

## 小贴士

- **窗口越大越吃性能**。真卡的话先降 `--cols`（比如 80），或者换 `--mode chars`。
- 终端字体建议选**等宽**字体，否则字符对不齐画面会歪。
- `chars` 模式的观感很依赖字体：`blocks` 阶梯配等宽字体最稳，`dense` 需要
  字体支持那些冷门符号，缺字会显示成方块。
- Windows Terminal / 新版 cmd 支持真彩色；很老的 conhost 请加 `--color 256`。
- 远程桌面或串口这种窄带宽场景，建议
  `--mode chars --cols 60 --fps 15 --color 256`。
- 投屏时如果画面全黑，试试 `--capture screen`（并把目标窗口放到最前面）。
- 投屏里点不中按钮是正常的 —— 一格字符大约等于目标窗口的 8 个像素宽。

## 已知限制

- 循环模式没有声音。
- 声音是「抽出来整段播」，不做逐帧同步；正常视频听感没问题，但如果视频中间
  有长时间静音再出声，可能会有轻微偏移。
- 不支持在线视频地址，只吃本地文件（需要的话可以先 `ffmpeg` 下载再播）。
- `chars` 模式下画面纵向分辨率比 `block` 低一半（一格只有 1 个像素），
  这是字符画本身的特性。
- 投屏不支持音频；全屏独占的游戏通常抓不到；目标程序卡住时 `PrintWindow`
  会跟着卡（改用 `--capture screen`）。
